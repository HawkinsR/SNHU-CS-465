In the full stack development of the Travlr Getaways application, two distinct frontend architectures were implemented to serve different user bases. The customer-facing frontend utilizes an Express application that renders static HTML pages using Handlebars templates. This traditional approach means the server generates the entire view and sends it to the browser for every page request. In contrast, the administrative side was built as an Angular Single Page Application (SPA), which relies heavily on JavaScript executing in the browser to dynamically update the view without full page reloads. This SPA approach provides a more seamless, desktop-like experience for administrators managing travel data. For the backend, a NoSQL MongoDB database was chosen over a relational database due to its flexibility with unstructured or semi-structured data. MongoDB stores data as documents, which directly aligns with how the application handles data models, such as trips and users, allowing for rapid iteration and scalability as the data requirements evolve.

A crucial aspect of connecting these distinct frontend and backend systems is JSON (JavaScript Object Notation). While JavaScript is a comprehensive programming language used to build the application logic, JSON is simply a lightweight, text-based data format that is easily readable by both machines and humans. In the Travlr application, the Express backend API queries the MongoDB database and formats the results as JSON, which the Angular SPA then consumes to render the administrative interface. Throughout the development process, refactoring code was a necessary step to improve functionality and efficiency. For example, moving raw HTML layouts into reusable Angular UI components, such as the `trip-card` component used in the administrative view, significantly streamlined development. These reusable UI components eliminated redundant code, ensured visual consistency across the application, and made future maintenance easier since updating a single component automatically updates every instance of it throughout the interface.

Ensuring that data flows correctly between the frontend and backend necessitates rigorous API testing of methods and endpoints. By utilizing tools like Postman, we could independently test GET, POST, PUT, and DELETE requests against specific API routes to verify that the backend controller logic correctly interacted with the database and returned the appropriate JSON responses. Testing became more complex with the addition of security layers, specifically the implementation of JSON Web Tokens (JWT) for the administrative login. To verify this security, testing methods had to account for both authenticated and unauthenticated states. We tested that protected endpoints, such as adding or editing a trip, would correctly reject requests lacking a valid token while seamlessly processing requests that included the proper authorization header, ensuring the application remains secure against unauthorized access.
